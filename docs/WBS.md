# WBS：从现在到能独立交付一个受治理的 agent

> 定稿于 2026-08-25。形态已定：**做工作台，不做平台**——按"将来能抽出平台"的规矩做。
> 每个里程碑按「FDE 能做到什么」定义，收尾要能演示、有验收报告、并写清还不能做什么。

## 0 · 目标

**终点**：一个人（现在是 Silas + Claude）能独立完成一次交付——拿到业务命题，接上企业系统
数据，组装一个受治理、能自己长技能的 agent，用可复现的验收报告决定能不能上线，交付之后靠
坏样本回流持续服务。同一件事做第二遍要明显更快，这是工作台成立的唯一标准。

**引擎形态**：开源 dsh 当引擎，只换 UI。交付物是**一整个 agent**，不是装进客户已有系统的
插件。我们钉死自己 vendored 的那份 dsh，不为任意版本做兼容。

**两条真实命题作为载体**：
- **校园网客服**（话术域）——材料齐（西安新路客服作业指导书），治理链已跑通。
- **123 云盘运营**（数据域）——连接层齐（`/sapi/` 已确认接口 + 自动续 token + 扒接口的方法）。

一条验治理，一条验连接与自成长。

### 0.1 什么时候翻牌成平台

不凭感觉，命中任一条就开始抽：**第三个客户** / **第一个不是自己人要用它** /
**同一段东西被复制粘贴到第三个地方**。在那之前守三条卫生：用到第二次的东西给它一个名字和
一条命令；客户专属的一律留在各自目录；验收链保持通用。做到这三条，翻牌那天是搬家不是重写。

### 0.2 和 FDE 本体论的关系

本体回答「这家企业有什么、口径怎么算」，我们回答「agent 能对它做什么、能说什么，以及凭什么
相信这套规矩是对的」。本体管名词，我们管动词的规矩。

对到那张架构图上：我们现在覆盖的是**动作 Actions** 与**权限**两格——「什么前提下允许调用」
「产出里什么不能外泄」「超出范围要怎么答」；技能库是 Actions 的实现，`propose_tool` 让
Actions 自己生长，治理保证新长出来的动作跑不掉。**对象与关系我们一格都没有**，连接层拉回来
的目前是裸字段。

值得记住的一点：本体层那张登记治理表（权威等级／责任人／更新时间／待复核）要解决的问题，
与我们已经解决的是同一个——一份资产凭什么可信、凭什么能上线、过期了谁负责。我们把
「填表 → 机械闸 → 考题 → 冻结 → 回流」这套在动词上跑通了，它能原样搬到名词上。

**本期取舍（2026-08-25 修订）**：完整本体不做，但**口径登记这一薄层要做，而且要前置**。
依据是行业实践核对——当前主流把领域建模前置到交付第一周，完全推后是偏离的；且数值类约束
（环比、使用率、分位）本身依赖指标口径，没有口径它们无从表达。口径登记只记「这个数怎么算、
字段从哪来、同名不同义怎么区分」，不建对象图、不做血缘。完整本体的时机仍是「第三个客户
开始重复」。

## 0.x · 横切约束（每个工作包都受它约束）

- **0.x.1 只读**：业务接口只允许 GET。`/sapi/user/sign_in` 是白名单里唯一的 POST（登录本身
  必须 POST）。任何回写一律拒绝，且有绕过测试盯着。
- **0.x.2 凭据隔离**：账号密码只从环境变量进程内读取。不进提示词、不进日志、不进会话记录、
  不进仓库。账号是 Silas 本人的生产后台账号，按本人使用对待。
- **0.x.3 真实数据不进仓库**：只在本机内存与本机临时目录。评测集用脱敏构造样本。报告只留
  结构与计数，不留业务数值。
- **0.x.4 交付纪律**：每个里程碑收尾能演示、有验收报告、写清还不能做什么。
- **0.x.5 语言口径**：对外产物使用书面专业语，术语以 `docs/MODEL.md` 为准；内部 FINDINGS
  与 STATUS 保留现有简称。
- **0.x.6 业务指标**：每个实例必须声明它负责的业务指标（基线、目标、采集方式）。只有验收
  通过而无业务指标的交付，回答不了「这次交付值不值」。
- **0.x.7 回流计量**：每次交付结束统计沉淀了什么回工作台。连续两次为零，说明在做一次性
  项目而非积累，需要停下来看形态。

## 现状（写清楚起点，免得高估）

已经有的：约束治理层（工具通道与说话通道，挂得进真 dsh，最小 profile 验过）；声明形态
（五种内置类型，一份 SOP 填过，三条填不进已登记）；验收链（机械闸免费 + 考题 + 替代话术交叉
验收，目前是几个各跑各的脚本）；`propose_tool` 的注册边界／占名防护／配额／回收；`badcase`
回流代码；一个 UI 插件形态的界面。

还没有的：一条命令的交付入口；一份通过闸的声明；起新实例的办法；连接器与口径登记；
只读技能与 GET 强制闸；产出物组装；自成长技能的审批流；回流在真实流量上跑过；
业务指标与回流计量。

**这份 WBS 的依据链**：`docs/STORYMAP.md`（FDE 用户故事地图，模块的推导依据）→
`docs/WORKSPACE.md`（处理台与分工线）→ `docs/MODEL.md`（对象、字段、状态机、不变量）→
本文件（里程碑）。改动顺序必须与依据链一致：先改故事地图，再改模型，最后改里程碑。

## M1 · 一条命令出验收报告

**增量**：对任意一份规矩声明跑一条命令，拿到能不能上线的判定，和一份能直接贴进交付记录的报告。

**完成判据**：campus 那份声明跑得出报告；四条判据实现并生效；退出码有语义；报告里的话不需要
写它的人在旁边解释。

- 1.1 CLI 骨架 `thymus deliver <声明>`，参数：轮数、模型、输出目录
- 1.2 判据引擎：考题齐全 ∧ 兜底句干净 ∧ 该拦全拦且不误伤 ∧ 三遍一致（跨轮聚合是新东西）
- 1.3 报告渲染：终端摘要 + markdown 报告，两级严重度（拦冻结／只提示）
- 1.4 冻结产物：通过才生成 `evals.frozen.json` 与哈希；不通过不生成
- 1.5 收编现有脚本：`check-spec-full`、`check-replacements` 并进同一入口
- 1.6 测试：假判定器跑全流程（不花钱）＋真模型跑一次留日志

## M2 · 第一份通过件

**增量**：拿到一份真正过闸的声明和冻结产物，同时得到第一份周期数据。

**完成判据**：campus 四条判据全绿；记录实际耗时与人工介入清单（改了几处、每处多久、重跑几次）。

- 2.1 D2 措辞收窄 → 重跑 → 数字对比
- 2.2 B2 误伤处理：改条款措辞 ／ 把该句纳入必放并调 topic，两条各跑一次取数
- 2.3 稳定性复跑：三轮加到五轮，看抖动收不收敛
- 2.4 周期数据记录
- 2.5 冻结归档：产物 + 报告 + 复现命令

**风险**：B2 那处更像判定器误判（把「向用户要学号」算成「说了账号内容」）。改不动本身是结论，
要写进能力边界，不许为了让报告变绿而删掉话术里的字段名。

## M3 · 起一个新实例

**增量**：在一个新目录里一条命令起一个客户实例——指定规矩声明、挂连接器、配技能白名单与
配额、带界面，得到一个能聊且约束生效的 agent。

**完成判据**：新开目录到能聊，十分钟内完成，且不用改任何代码。

- 3.1 实例目录约定：声明、连接器配置、技能白名单、界面配置各在哪
- 3.2 插件配置化：声明路径、兜底句、免检工具表、provider/model 全从 config 读
- 3.3 起实例命令：生成最小 profile、拷源码、起进程（现在 `shell.sh` 里那套固化下来）
- 3.4 校园网客服实例作为第一个样板

**注意**：不做打包、不做 peerDeps 对齐、不写给外人的上手文档——那些是翻牌之后的事。

## M4 · 连接层、口径登记与只读技能

**增量**：把一个真实企业系统接进来——连接器可用、指标口径已登记、已确认接口封装为只读技能，
agent 能对真实数据问答。

**完成判据**：非 GET 被代码拒绝且有测试；凭据不出现在任何日志或会话；至少四个接口成型；
至少五条指标口径登记为「已确认」；产出一份「它能看什么、看不到什么」的报告。

- 4.1 连接器对象化：地址、认证、续期、已确认接口、发现方法（凭据只记来源，不记值）
- 4.2 **GET 强制闸**：工具层强制；认证 POST 属连接器内部行为，不暴露为技能；带绕过测试
- 4.3 口径登记：指标怎么算、字段从哪来、同名不同义怎么区分，逐条确认责任人
- 4.4 技能封装：用户分端统计、收入按端、订单列表（含 channel）、大客户台账
- 4.5 数据治理约束写成声明：哪些字段不外泄、未授权不给明细、聚合与明细的边界——走 M1 的闸
- 4.6 真实链路验收：本机跑，日志脱敏
- 4.7 会话演示：用 M3 的实例问几个真问题

**为什么前移**：整合墙是多数 AI 交付真正的失败点，也是 FDE 价值最集中的地方；领域建模
（我们这里是口径登记）在主流实践中被前置到第一周。原计划把这两件排在治理之后，顺序是反的。

**风险（预判会命中）**：现有五种约束类型管不了「环比降 50%」「使用率 ≥90%」这类数值口径。
4.5 大概率撞墙，撞墙清单是这一轮的主要产出之一。口径登记先行会让这份清单更准确——届时
分得清是「缺类型」还是「缺口径」。

**次要风险**：token 绑 IP、单账号并发限制，可能影响跑批节奏。

## M5 · 产出物组装

**增量**：FDE 能配出 agent 定期生成并投递的东西——日报、预警、看板，也就是业务方每天真正
打开的那一层。

**完成判据**：至少一种产出物按时生成并投递成功；其内容与对话一样经过说话通道治理，不因
「不是对话」而绕开字段抹除；能记录采纳情况。

- 5.1 产出物对象：类型、触发、渠道、模板、采纳记录
- 5.2 生成链路：数据取自技能，内容过治理，投递到渠道
- 5.3 以 B123 现有日报与预警为第一个样板，与既有脚本对齐口径
- 5.4 采纳记录：打开、回复、被引用

**为什么必须有**：治理本身业务方看不见。缺这一层，交付物在业务方眼里只是一份验收报告。

## M6 · 让它自己长技能

**增量**：不再逐个写接口。agent 按「扒接口」那条路子提出新技能，宿主按配额与白名单审批，
回收有据可查。

**完成判据**：agent 能提出技能；未审批不可用；配额上限真链路验到；回收后不可再调；
**新技能自动纳入治理与回流**，不是长完就脱管。

- 5.1 `propose_tool` 接进这个域
- 5.2 技能提案的形状：接口路径、参数、返回、用途、风险
- 5.3 审批流：谁批、批什么、拒绝理由回传给 agent
- 5.4 GET-only 与字段治理对新技能自动生效，不靠 agent 自觉
- 5.5 端到端：从「我想看渠道归因」到提案、审批、可用，全程留痕

**已知约束**：模型判不了自己写得对不对（发现 22 已验），所以审批必须是人或确定性规则，
不能是 agent 自评。

## M7 · 回流即服务

**增量**：坏样本从实例回到评测集，出版本对比，发新版本。影子运行是它的第一步。

**完成判据**：老规则（`核心.py` 里那几条阈值）与新 agent 跑同一天数据，出差异清单，且每条
差异能判断是谁的问题；坏样本并进评测集而不把评测集磨钝。

- 6.1 影子跑法：同数据、双路径、差异记录
- 6.2 口径对齐报告：哪些差异是新的错、哪些是老规则本来就有的问题
- 6.3 回流接入：`badcase` 现有代码接到这个域
- 6.4 版本对比：这一版比上一版好还是差

## M8 · 第二个客户目录

**增量**：同一套工作台同时跑校园网客服与 123 云盘运营两个实例，规矩、技能、数据互不串。

**完成判据**：两个实例并存，任一实例的声明或技能改动不影响另一个；共用的部分被识别出来并
只有一份。

**这一步的真正产出**：哪些东西被复制了第二次——那份清单决定翻牌信号什么时候到，也决定
本体该不该上马。

## M9 · 资产台账与结果度量

**增量**：一条命令看清两件事——工作台在长什么，以及这次交付值不值。

**完成判据**：清单数字全部来自实际产物；每个实例能给出其业务指标的基线与当前值；能算出本次
交付回流了几件。

- 9.1 资产统计：声明模板、连接器、口径条目、技能、样例集、实测结论及各自复用次数
- 9.2 回流计量：本次交付沉淀回工作台的件数；连续两次为零即告警
- 9.3 业务指标跟踪：基线、目标、当前值

**注意**：资产部分给自己看，业务指标部分对业务方说话。两者口径不同，不要混在一张表里。
