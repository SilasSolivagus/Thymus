# 处理台与分工线

> 工作台只有**一个工作场所**：处理台。其余模块一律是看板或入口——它们呈现状态、提供跳转，
> 不承载操作。判断分散在多个界面里做，是工作台退化成脚本集合的第一步。
> 定稿 2026-08-25。

## 1 · 为什么需要一个统一工作场所

FDE 每天真正做的事只有一类：**对一个待定项做出判断**。这个待定项可能是一条尚未编译的
SOP 条款、一条验收不通过的约束、一个 agent 提出的技能、一条昨日回流样本。它们分属不同模块，
但形态相同——都是「有材料、有证据、需要人拍板、拍完要留痕」。

按模块分开做有两个代价：一是同一时刻要在几个界面之间判断先做哪个；二是每个界面各自演化出
自己的决策记录格式，判断沉淀不下来。

## 2 · 处理台的结构

三栏，从左到右是「选什么—看什么—定什么」。

**左栏 · 队列**
所有待定项统一为一种对象（见 3），按是否需要人工介入排序，不按类型分组。
类型只是标签，不是分区。

**中栏 · 材料与草案**
- 原始材料：SOP 条款原文、接口返回样例、回流样本的完整会话。
- 平台 agent 的草案：编译成哪种约束类型、body 怎么写、候选措辞有哪几种。
- 客观证据：静态自检结果、闸的评分、历史相似案例。

**右栏 · 决策与沉淀**
- 可选动作：采纳草案／修改后采纳／驳回／标记为不可覆盖。
- 必填的一行理由。这一行不是流程装饰——它是知识资产的最小单位（见 4）。
- 本次判断将沉淀成什么，在提交前就显示出来。

## 3 · 待定项 WorkItem

统一抽象。各模块产生它，处理台消费它。

| 字段 | 类型 | 说明 |
|---|---|---|
| id | string | |
| instanceId | ref | |
| kind | `条款待编译` \| `验收问题` \| `技能待审批` \| `回流样本` \| `未覆盖条款复核` | |
| source | object | 指向原始对象（条款、Issue、Skill、ReturnedSample） |
| evidence | object | 客观证据：闸的结果、评分、统计 |
| draft | object? | 平台 agent 的草案，可为空 |
| decision | object? | 动作、理由、决策人、时间 |
| status | `待处理` \| `已处理` \| `已搁置` | |

## 4 · 分工线

三类，划线依据必须是实测结论或机制事实，不凭感觉。

### 4.1 系统做（确定性，零成本，不问模型）

| 事项 | 依据 |
|---|---|
| 样例完整性静态自检：三组是否齐全、留出是否伪装、必拦必放是否矛盾、未覆盖是否为空 | 这几类错误是字面可判的，留给人只会漏 |
| 跨轮聚合与判定稳定性 | 人横向比对三行数字必然出错 |
| GET 强制、配额上限、技能占名检查 | 机制约束不能依赖自觉 |
| 回流样本的确定性分流 | 已实现 |
| 报告渲染、冻结产物与哈希 | 纯机械 |

### 4.2 平台自己的 agent 做（要模型，结果必须经人确认）

| 事项 | 为什么可以交出去 | 为什么仍需人确认 |
|---|---|---|
| 条款 → 约束类型草案 | 选型这件事模型做得对：三版声明的类型选择全部正确 | 缺口会被硬套进最接近的类型，人要判「这条其实表达不了」 |
| 失败条款的候选措辞 + 预跑闸打分 | 今天实测过：7 条候选自动打分，2 条通过 | 采纳哪条是产品决定，且可能一条都不该采纳 |
| 接口发现与技能脚手架 | 扒接口是可复制的机械流程 | 风险标注与是否启用由人定 |
| 回流样本初步分类与聚类 | 相似样本可自动归并 | 判定未拦截还是误拦要人看 |
| 验收报告初稿措辞 | 结构固定 | 对外口径要人过 |

### 4.3 FDE 做（不可替代，每条都有实测依据）

| 事项 | 依据 |
|---|---|
| 编写同义泛化样例 | 出题 agent 只看得到声明本身，生不出「声明没列但语义同类」的说法（发现 05 第 3 条） |
| 判定「这条表达不了」 | 模型从不主动说这句话，只会硬套（发现 22） |
| 拆开混写的条款 | 一条里混了义务与禁止时，无条件那半会被有条件那半吃掉；拆开后留出集从 3–4/5 升到 5/5（发现 20） |
| 调措辞 | 唯一没有机械检查的一环，只能改完重跑看数字 |
| 审批技能提案 | 模型判不了自己写得对不对，自评几乎全绿而共同标尺必拦仅 8–9/13（发现 22） |
| 与客户沟通口径与取舍 | 不是技术问题 |
| 冻结决策、接受已知限制 | 要承担责任的人来定 |

**这条线会移动，但只能凭数据移动**：某项交给 agent 之后，其结果被人驳回的比例若持续低于
阈值，才允许把它从 4.3 移到 4.2；反之要移回来。移动记录留档。

## 5 · 知识资产：每次判断沉淀成什么

FDE 的判断如果只体现为一次点击，工作台就不会变快。每类判断都要落成可被下次复用的东西。

| 判断 | 沉淀物 | 下次怎么用 |
|---|---|---|
| 条款归入某个约束类型 | 条款→类型映射案例（含原文片段） | 平台 agent 提草案时作为示例检索 |
| 判定不可覆盖 | 不可覆盖条款库（条款原文 + 理由 + 当时用什么顶着） | 遇到相似条款直接给出先例，避免重复论证 |
| 修订措辞 | 措辞候选与闸评分记录（哪些改法有效、有效多少） | 同类问题直接给候选，不从零想 |
| 审批或拒绝技能 | 审批先例（批了什么、拒了什么、理由） | 新提案先与先例比对 |
| 编写同义泛化样例 | 表达族库（按语义类别组织，跨客户可复用） | 新客户同类约束的样例起点 |
| 标注回流样本 | 判定记录 + 并入去向 | 版本对比的依据 |

**闭环**：FDE 的判断 → 沉淀物 → 平台 agent 草案质量提升 → 需要人判断的项减少 →
第二次交付更快。这条闭环是「工作台成立」的机制解释，不是口号；资产台账那一屏统计的就是它。

## 6 · 模块定位（重新划分）

| 模块 | 定位 |
|---|---|
| **处理台** | **唯一工作场所**：所有判断在这里做，所有沉淀在这里产生 |
| 客户实例 | 入口：切换当前实例 |
| 约束声明 | 看板：版本状态与覆盖情况，点进去回处理台 |
| 验收报告 | 看板：结论与证据，问题项点进去回处理台 |
| 技能 | 看板：已启用与待审批，审批动作回处理台 |
| 运行观察 | 入口：以用户视角实走，发现问题生成待定项 |
| 样本回流 | 看板：队列与统计，标注动作回处理台 |
| 资产台账 | 看板：沉淀物与复用次数，验证闭环是否成立 |
