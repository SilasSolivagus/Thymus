# 关键发现 01：agent 对用户的「说话」绕开工具管线

`DEMODIR=campus DEMO=probe-multiturn`，真 DeepSeek，最小多轮探针。

## 观察

- 追问填槽行为正确：用户模糊输入（「我上不了网」「我是西大的」）时，agent 没有
  用不全信息瞎调工具，而是追问学号+手机号；信息齐了才调 lookup_account。
  **你担心的多轮填槽，模型自己会做。**
- 但整段对话 reply 工具调用 = 0。尽管 persona 明确要求「所有面向用户的话都通过
  reply 发」，agent 全部用 assistant 直接文本回复用户，一次都没走 reply。

## 这为什么是根本性的

我们全部约束机制都挂在工具调用上：
- 禁语过滤 / 内部字段脱敏 → tools/post-execute 改写工具产出
- 认人前置 / 槽位校验 → tools/pre-execute 拦工具调用

但客服 agent 最核心的产出——**它对用户说的每一句话**——是 assistant 消息，
不是工具调用。它绕开了整条 tools 管线。

于是出现一个结构性错配：
| 约束对象 | 是不是工具调用 | 我们拦得到吗 |
|---|---|---|
| 调哪个业务系统、系统返回什么 | 是 | 拦得到 |
| **对用户说什么（禁语、内部信息外泄）** | **否，是 assistant 直接输出** | **拦不到** |

对客服 agent，「说什么」就是产品，而最重要的合规约束（服务禁语）正好落在
「说什么」上——即我们当前机制拦不到的地方。

对比删文件场景才看清差别：删文件的危害动作 delete_file 本身是工具调用，拦得住；
客服的危害动作「说禁语」是模型的直接输出，不是工具调用，拦不住。

## 可能的出路（未验证，下一步逐个试）

1. **强制说话走工具**：把 reply 设为唯一出口，用 agent/pre-step 或输出拦截强制
   模型不能直接产出面向用户的文本，必须调 reply。问题：模型不配合（本探针已证），
   要靠机制强制，而不是靠 persona 请求。
2. **拦在 agent 循环层而非工具层**：dsh 有 agent/pre-step 等主循环 waterfall，
   禁语过滤可能得挂在「assistant 消息提交前」这个点，而不是工具执行点。需确认
   dsh 有没有「assistant 输出提交前」可拦截的事件。
3. **承认边界**：说话类约束不属于工具 policy 层能管的范围，需要不同的机制。

## 意义

这不是 bug，是把「policy 层约束」用到「对话 agent」上时的真实边界。之前所有 demo
的危害动作都恰好是工具调用，掩盖了这个错配。真实客服场景第一次把它逼出来——
这正是「先跑再看」的价值：坐着推演推不出这一条。
