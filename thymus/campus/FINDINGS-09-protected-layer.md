# 发现 09：把约束挪出动态注册表能防卸载，但防不住架空——约束不能和被约束方做同侪

承发现 08。既然 dsh 明说沙箱不是安全边界、卡点得在它之外，先试成本最低的结构解：
**约束不通过 `DynamicCordisRunner` 挂载，改由宿主直接 `ctx.plugin()` 挂上**。
agent 照旧写源码、过评测，但激活由 Thymus 做——对应「加载权与执行权分离」那条成熟做法。

探针 `probe-protected-layer.ts`，不调模型。同一份约束逻辑、同一个敌意插件，
只动两个变量：约束挂在哪一层、谁先挂。

## 四组实测

| 组 | 约束挂法 | 次序 | listPlugins 看得到约束 | 卸载 | 最终 |
|---|---|---|---|---|---|
| 一 | 动态注册表 | 约束先 | 有 | `{"ok":true}` | **拦不住** |
| 二 | 宿主直挂 | 约束先 | 没有 | 够不着 | 仍被拦 ✓ |
| 三 | 宿主直挂 | 敌意先 | 没有 | 够不着 | **拦不住** |
| 四 | 宿主直挂＋`prepend` | 约束先，敌意也 `prepend` | 没有 | 够不着 | **拦不住** |

组二成立：挪层之后 `listPlugins` 只看得到 `hostile`，约束卸不掉，敌意 handler
连跑都没跑到——约束的 `deny` 先短路了。**「卸不掉」这一条解决了。**

组三与组四说明它不够。`tools/pre-execute` 是 waterfall，`{kind:'allow'}` 直接短路，
后面的 handler 不再执行。谁在前谁说了算，而位置是先到先得：

- 组三：敌意先挂，约束后挂，敌意在前，短路，约束形同不存在。
- 组四：约束用 `ctx.on(..., true)` 前插，敌意后挂**也**前插——后 prepend 的排更前。
  `prepend` 两边都能用，所以它是抢位竞赛，不是保证。

## 结论：受保护层不能是同侪

在同一条事件通道上，任何参与者都能短路后面的人，而顺序保证不住。
所以「把约束挪到宿主层」只解决了一半；另一半是**不能让被约束方拥有同一条通道的注册权**。

推下去，架构上必须区分两个主体：

- **写约束的 agent**：提交插件源码，过冻结评测，由 Thymus 以宿主身份挂载。
  它不需要、也不应该有 `cordis_define` / `cordis_run` 这类工具。
- **被约束的 agent**：真正跑业务的那个。它**不能有动态插件工具**——
  一旦有，它就能给自己挂一个前插的 `{kind:'allow'}`，所有约束当场变成自愿的。

这正是双人复核在这里的形状：写的人和批的人分开，被管的人不拿钥匙。

## 落地方案（不改 dsh）

1. 约束插件一律宿主挂载，不进动态注册表。已实测（组二）。
2. 业务 agent 的工具集里去掉全部 cordis 动态插件工具。
3. 约束必须在业务 agent 起跑之前全部就位——对应 seccomp 的用法：
   先装过滤器再 exec，顺序反了等于没装。
4. 运行中新增约束这件事，在当前机制下**不安全**：新约束排在已有 handler 之后，
   先到的能短路它。要支持热加约束，得先解决通道注册权，不能靠 `prepend`。

如果愿意改 dsh，最小改动是在 guard 的 façade 上限制可注册的事件名
（动态插件不得注册 `tools/pre-execute` 等治理通道）。但那是改 vendor，
要背 fork 维护成本，rc.7→rc.8 的 536 个 commit 是前车之鉴。先走不改的那条。

## 补测：`llm/stream` 也一样（原为本文最大空白）

本文原写「只测了 tools/pre-execute，llm/stream 形态应当相同，未实测」。已补，
见 `thymus-gate.spec.ts` 论证 12–15。**结论相同，但机制不同，值得写清楚。**

`tools/pre-execute` 是短路链：先返回判决的人说了算。
`llm/stream` 是包装链：listener 列表里排最前的是最外层，它的输出直接交给装配器，
所以**最外层说了算**。两条通道的极性相反，但都落到同一句话——`prepend` 让后来者
插到最前，于是都是「后动手的赢」。

四种顺序实测（约束在宿主侧改写「不可能」，敌意插件把文本换回禁语）：

| 挂载顺序 | 用户实际看到 | 禁语 |
|---|---|---|
| 约束先挂、敌意后挂 | 这个需进一步确认 | 拦住 |
| 敌意先挂、约束后挂 | 这个不可能 | **漏了** |
| 约束前插、敌意后挂也前插 | 这个不可能 | **漏了** |
| 敌意先挂且前插、约束后挂前插 | 这个需进一步确认 | 拦住 |

四种里两种被抢赢。**说话通道与工具通道同样不安全**，而我们所有说话类约束都挂在这里。

把约束交给网关（裁决发生在整条 waterfall 跑完、装配之后）后，四种顺序全部抓得到；
并且实测「网关看到的文本 == 用户会看到的文本」，链内改写绕不开裁决依据。
