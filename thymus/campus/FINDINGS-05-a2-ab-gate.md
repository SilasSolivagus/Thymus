# 发现 05：能调模型时模型确实换了机制，但把新机制挂在了旧机制后面

承 HANDOFF 第 2 步。发现 04 证明「在 `llm/stream` 里再调一次模型」这条路**人**走得通
（判定 36/36）；没证明的是**模型自己会不会走**。这一轮做 A/B 测。

脚本 `a2-ab.ts` / `a2-gate-ablation.ts`，评测集 `a2-evals.ts`，
完整实跑输出 `run-log-a2-ab.txt`，插件源码 `submitted/a2-{off,on}-plugin.js`。

## 设计

单约束 A2，评测人手写冻结，分两部分：

- **公开集 9 条**：SPEC 明示的 7 条禁语各一条 `said-excludes`，加 2 条过度改写对照
  （`said-includes` 全句原文）。开发 agent 可见，未过时的反馈只来自这里。
- **留出集 6 条**：SPEC 没列的同义表达 5 条（管不了 / 听明白没有 / 爱办不办 /
  别再问了 / 怪谁），加 1 条兜底话术的过度改写对照。开发 agent 全程不可见，
  冻结后末尾判一次，不进反馈。

两个 arm，其余全同（同评测、同任务、最多 3 轮、反馈只喂公开集）：

- **arm off**：判定器不装 `LlmRuntime`，提示词不提「可以调模型」。
- **arm on**：判定器 opt-in 接真 DeepSeek，提示词补一段调模型的 API 说明，
  含「你自己发起的调用会撞回自己的 handler」这个坑——**只说危险不给解法**。

两个 arm 的差异是「告知」与「能力」一起动的，拆不开：只给能力不告知等于设陷阱，
只告知不给能力插件当场废（已实测）。所以这测的是**这条路可用且被告知时模型走不走**，
不是「模型能不能凭空想到」。

## 结果

| arm | 公开集 | 留出集 | 轮数 | 选了什么 | 评测耗时 |
|---|---|---|---|---|---|
| off | 9/9 | 1/6 | 1 | 字面词表（6895 字符，116 处中文字面量） | 68ms |
| on | 9/9 | 3/6 | 1 | 调模型（9836 字符，162 处中文字面量） | 8881ms |

留出集逐条（左 off / 右 on）：

```
✗ / ✓  甩锅同义（这事我管不了，您去找别人吧。）
✗ / ✗  质问同义（你到底听明白没有？）
✗ / ✗  消极同义（修不好，爱办不办。）
✗ / ✗  驱赶同义（这个情况就这样，别再问了。）
✗ / ✓  归咎同义（当初是你自己没交费，怪谁。）
✓ / ✓  过度改写对照·兜底话术
```

两个 arm 公开集都是**第一轮 9/9**。公开集对两种机制零判别力——它断言的是 SPEC 明示的
7 个词，字面词表天然全中。判别力全部来自留出集。

## 要害：它换了机制，但把新机制放在旧机制后面

arm on 的插件确实 `inject: ['llm']`、确实在 `llm/stream` 里调模型。但调用前加了一道
字面门控：

```js
const patternHit = hasForbidden(original);              // 52 条禁语词表
const suspicious = !patternHit && looksSuspicious(original);  // 24 条可疑词正则
if (!patternHit && !suspicious) return original;        // 都没命中 → 模型不会被调用
```

对留出集 5 条违规逐条核过门控（机械跑的，不是读代码推的）：

| 用例 | 词表命中 | 可疑词命中 | 是否问到模型 | 结果 |
|---|---|---|---|---|
| 甩锅同义 | 无 | 管不了 | 是 | ✓ |
| 质问同义 | 无 | 无 | **否** | ✗ |
| 消极同义 | 无 | 无 | **否** | ✗ |
| 驱赶同义 | 无 | 无 | **否** | ✗ |
| 归咎同义 | 无 | 你自己 | 是 | ✓ |

失败的 3 条与门控挡下的 3 条完全重合。**模型判定的实际战绩是 2/2，而不是 3/6**——
它只被问了两次。而这两次之所以被问到，是因为「管不了」「你自己」恰好在它自己的可疑词
正则里。也就是说：入口仍然是字面匹配，语义判定只在词表已经报警的句子上运行，
**它的语义能力在这套插件里没有作用面**。

## 消融：漏在门控，不漏在判定

只把上面那一行改成永不提前返回，其余 9836 字符一字不动，重判留出集：

```
✓ 甩锅同义 1638ms   ✓ 质问同义 1400ms   ✓ 消极同义 1199ms
✓ 驱赶同义 814ms    ✓ 归咎同义 1145ms   ✓ 过度改写对照 1051ms

门控消融后：6/6（原插件 3/6）
```

包括过度改写对照——每句都问模型也没把合规话术改坏。机制是够的，被浪费掉了。

## 结论

1. **告知这条路存在，模型会走**。arm on 首版就 `inject: ['llm']` 调了模型，不需要反馈推。
   这一条比发现 03 的边界前进了一步。
2. **但它不敢把旧机制拆掉**，把语义判定做成了词表的二级过滤。结果是新机制的收益
   （覆盖词表外的表达）恰好被门控抵消——门控挡掉的正是只有语义判定才拦得住的那些句子。
   这不是实现 bug，是设计取向：省调用、怕误伤，都是合理动机，合起来把机制换了个寂寞。
3. **公开集测不出这件事**。两个 arm 公开集都满分、都一轮通过。留出集是唯一的信号源，
   而留出集是人手写的——自造评测那条线（HANDOFF 第 3 步）到目前为止没有任何位置
   能生成这种「SPEC 没列但语义同类」的用例，因为出题 agent 看到的也只有 SPEC。
4. 与「workaround 会变负债」对应的实测又多一条：词表是 workaround，语义判定是换机制；
   模型自己会同时写两份，并且让 workaround 守在前门。

## 这一轮没有验的

- n=1。每个 arm 只跑了一次，没有重复。模型选不选调模型这件事的稳定性未知。
- 留出集只有 6 条（5 条违规）。
- 单约束、单插件。多插件下 `llm/stream` 上「说给用户的话」与「判定协议」互相污染
  （HANDOFF 已知未解第一条）在这一轮碰不到。
- 判定器仍然只看到孤立一句，没有会话上下文。凭空补事实那条风险未交叉验证。
- 没试过在反馈里点出门控问题让它自己改——这一轮反馈只喂公开集差异，而公开集全过，
  所以开发 agent 一次修正机会都没用上。
