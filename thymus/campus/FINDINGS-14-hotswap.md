# 发现 14：热替换是干净的，但换版会让决策途中的调用失败——方向是不放行

「自生长」拆成写得出／能热替换／能卸载重写三件。前面一直只验了一部分——我们所有的
替换都是「重新写一版，在全新 context 里重挂再评测」，**从没测过运行中的 agent 把自己
身上正在生效的插件换掉**。这里补上。

测试 `thymus-hotswap.spec.ts`（论证 23–27），不调模型，确定性。
dsh 的替换 API 是 `run(agent, pluginId, packageId, 'update')`：同一个 pluginId 下追加
新 package 再切过去，旧版由 `retract()` 卸载（splice 掉全部 handlerDisposers 并
dispose fiber）。

## 干净的部分

| # | 论证 | 结果 |
|---|---|---|
| 23 | 新版立即生效 | 判决理由来自 v2，**没有 v1 残留** |
| 24 | 换成宽松版后旧约束真的失效 | 原来被拦的调用放行了——旧 handler 卸干净了 |
| 25 | 说话通道同样换得动 | 产出是 `[v2]您好` 而不是 `[v2][v1]您好`，两版不叠加 |
| 26 | 换版不打断飞行中的工具执行 | 慢工具正常返回 |

论证 26 的适用范围要说清楚：约束在**派发之前**就判完了，所以那时工具已在执行、
handler 早已退场。这条只说明换版不会打断已经在跑的工具，**不说明决策途中换版会怎样**。

## 决策途中换版：调用直接失败

论证 27 才是真问题。让 v1 的 handler 故意慢（拿到调用后等 200ms 再给判决），
换版就落在这段窗口里：

```
这次调用的结果：Error: Context has been disposed
既不是 v1 拒绝，也不是 v2 拒绝
```

原因是 `retract()` 会 dispose 旧插件的 fiber，而这次决策挂在那个 fiber 的
timer 效果上。**我原先猜的是「由发起时那一版给出判决」，不对。**

要紧的是失败方向：调用**没有被放行**（产出里没有 `deleted`）。所以热替换在压力下
会产生一批失败的调用，但不会产生绕过约束的调用。**吵，但是安全的。**

换版之后的新调用正常走新版。

## 顺带记两条沙箱事实

- 动态插件里**用不了 Node 定时器**。`setTimeout` 会被拦，错误信息直接教你改用
  `inject: ['timer']` + `ctx.timeout(ms)`——这是 fiber 效果，插件停掉时自动清理。
  也正因为它是 fiber 效果，才有了上面那个「换版 → Context disposed」的现象。
- `plugin.idPrefix` 必须是 **3–6 位纯小写英文字母**，带数字会被拒。

## 对「自生长」的结论

能力这一侧，热替换这条路是通的：换得成、旧版不残留、两版不叠加。
所以「自生长」缺的不是热替换能力，仍然是那两样——**判断该不该换的信号**，
以及**不让被约束方自己动这个开关的权限设计**。

## 没验的

- 只测了单插件的自我替换。多个插件同时换、或换的过程中另一个插件在跑，没测。
- 没测「换到一半失败」——新版挂载抛错时，旧版是留着还是也没了。
- 决策途中换版的失败率与并发量的关系没测；只知道会失败，不知道在真实负载下多频繁。
