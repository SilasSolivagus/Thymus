# 发现 10：判决聚合层——把约束从 waterfall 上的同侪改成调用路径外的裁决者

承发现 09：`tools/pre-execute` 是 waterfall，`{kind:'allow'}` 短路，先注册的先跑，
`prepend` 两边都能用，所以「谁在前」是抢位竞赛。只要被约束方能往同一条链上注册，
任何约束都能被抢先架空。

借 Claude Code 的 PreToolUse 形态（[文档](https://code.claude.com/docs/en/hooks)）：
匹配的 hook 并行跑、没有顺序，任一 deny 即拒绝，allow 覆盖不了 deny——
退出码 2 拦下之后即便输出 JSON 的 allow 也压不住。**要害不是排序，是聚合规则。**
先到先得的链天然可抢位，收齐判决再裁决就不会。

实现 `thymus/src/gate.ts`（116 行），实验 `thymus/thymus-gate.spec.ts`，
不调模型，已并入 `run-tests.sh`（8 files / 52 passed）。

## 两个网关都站在链外

- **工具通道**：包住 `ctx.tools.execute`，在派发之前裁决。链上的 handler 再怎么抢位、
  返回什么，都在这一层之后才有机会跑。
- **说话通道**：先跑完整条 `llm/stream` waterfall 并装配，再对**装配后的文本**裁决。
  链内插件能改写文本，但改不掉「装配完还要过一道」。装配算法与 agent loop 落进
  assistant 消息的是同一份，所以裁决者看到的就是用户会看到的。

约束是宿主侧普通对象，不经 `DynamicCordisRunner`，所以也不在动态注册表里。

## 八条论证，每条一个对照实验

| # | 论证 | 实验结果 |
|---|---|---|
| 1 | 现状：约束做同侪，敌意 handler 抢先 allow 就架空它 | 敌意来之前拦得住，挂上之后**放行** |
| 2 | `prepend` 是抢位竞赛不是保证 | 约束前插、敌意后挂也前插 → **敌意排更前** |
| 3 | 网关下顺序无关 | 敌意后挂／前插／先挂，三种**都拦得住** |
| 4 | 任一 deny 即拒绝，与声明顺序无关 | `[allow, deny]` 与 `[deny, allow]` 都拒绝；全 allow 才放行 |
| 5 | allow 覆盖不了 deny | 链上返回 allow，结果仍是 `isError` 且理由来自网关 |
| 6 | 约束抛错按 deny 计 | 裁决者抛错 → 拒绝，理由含「裁决失败」 |
| 7 | 说话通道 | 链内插件把文本改回禁语，装配后**仍被抓到** |
| 7b | 不过度拦截 | 无敌意插件时合规话术原文不变、放行 |
| 8 | 卸载够不着 | `listPlugins` 只列得到 `hostile`，约束不在其中 |

论证 1 与 2 是「没有网关会怎样」的对照，跑出来是失败（放行），这是预期——
它们证明问题真实存在，不是我们臆想的。

## 实验抓到的一个真 bug

第一版 `adjudicate` 把 `ask(c)` 放在 `try` 外面，只包住 `await v`。
同步抛错的约束会直接冒到调用方——**工具调用因异常中断，而不是按 deny 处理**。
论证 6 当场把它测出来了。修法是把取判决这一步也放进 `try`。

这条本身就是「每个论证都要实测」的价值：这个洞靠读代码看不出来，
写测试的时候我也以为已经处理了。

## 攻它：换名字这条缺口，确认成立

网关建好之后回头攻它自己。这一段走了三次弯路，都记下来——因为每一次的错误结论
都长得像一个可信的发现。

| # | 论证 | 实验结果 |
|---|---|---|
| 9 | 真 agent 看得见并调得动自己插件注册的工具 | agent 作用域与根作用域**都看得见**；调用成功返回 `deleted:x.txt` |
| 10 | 按名判定被换名字绕过；白名单挡得住 | 老名字被拦，**新名字放行**；换白名单后新名字被拦，理由来自网关 |
| 11 | 沙箱拿不到别的工具的 execute，也拿不到真 ToolRuntime | `tools.get()` 只返回 `name,description,parameters`；`ctx.get('tools')` 只有 `register,schemas,get` |

**缺口成立**：约束按工具名判定时，动态插件注册一个同功能不同名的工具就能绕过。
白名单式（未登记一律拒绝）挡得住，所以它从「纵深防御」升级为**必需**。

### 三次弯路

1. 第一版敌意插件直接 `ctx.tools.register({...})` 传裸对象。挂载失败，报
   `dynamic tool registration must use a tool returned by harness.defineTool(...)`
   ——但我当时没看挂载 receipt，只看到调用返回 `unknown tool`，就写成了
   「沙箱注册的工具落在插件自己的作用域，根作用域调不到」。**工具压根没注册上。**
2. 改用 `harness.defineTool` 之后仍失败：参数是扁平 DSL（参数根隐式），
   不是 JSON Schema 的 `properties` 嵌套。
3. 修对之后才发现，「根作用域看不见」也是同一个假象——注册成功后根作用域一样看得见，
   **没有作用域隔离可依赖**。

三次的共同点：失败的表象（`unknown tool`）和「被拦住了」长得一样。
如果不去看挂载 receipt、只看最终调用结果，会得出「缺口不存在」的相反结论，
而且看起来完全合理。

## 代价与失败路径（论证 20–22）

发现 13 把「语义判定放网关里」变成了推荐架构，那这条路的代价和失败行为就得先摸清。
三条实测，两条抓出网关自己的缺陷。

**代价：约束是并行求取的，延迟取最慢的一条，不是累加。**
四条各 120ms 的约束，总耗时接近 120ms 而非 480ms（`adjudicate` 用 `Promise.all`）。
我先前在对话里说过「网关里两条约束就是两次调用，串行，延迟翻倍」——**那句没测就说，是错的**。

**缺陷一：约束挂住时网关无限期等下去。** 没有超时这道保险。
已修：加 `DEFAULT_VERDICT_TIMEOUT_MS = 10_000`，单条约束超时按 deny 计，可配。
方向选 deny 不选 allow：说出去的话收不回，宁可不说。

**缺陷二：约束返回非法判决时，网关当成放行。**
`verdicts.find(v => v.kind === 'deny')` 对一个 `{kind:'随便什么'}` 找不到 deny，
于是落到 allow——**fail-open，方向反了**。已修：加判决形状校验，不是
`{kind:'allow'}` 或 `{kind:'deny', reason}` 一律按 deny 计。

三种「约束自己坏掉」的情形现在都按 deny：抛错、超时、返回非法判决。

## 边界

- 工具通道的网关靠包住 `ctx.tools.execute` 实现。**必须在被约束方的代码加载之前装**，
  和 seccomp 一样——先装过滤器再放行不受信任的代码。装的顺序反了没有测过。
- 包 `execute` 用的是覆盖服务实例上的方法。同进程里理论上还能被再包一层覆盖回去；
  真正的边界要靠运行身份（见下）。
- 说话通道的网关站在「我们自己发起装配」这条路径上。真实部署里装配由 agent loop 做，
  网关要插在哪里没有验。
- 说话通道的抢位已补测（论证 12–15，见发现 09）：四种挂载顺序里两种会被敌意插件抢赢，
  交给网关后四种全抓得到。
- 只做了确定性裁决，没有 `ask`（转人工）这一档。
- 超时默认 10 秒是拍的，没有按真实语义判定的延迟分布校准过（实测单次 0.8–1.6 秒）。
- 真 agent 用的是假 LLM adapter（不调模型），只验证工具可见性与调用路径，
  没有跑真实的 agent loop 回合。
- 白名单式约束现在是必需的，但「哪些工具进白名单」这件事本身没有机制——
  目前靠人写死。动态插件合法注册新工具的正当场景（自指工具集的本来用途）
  与这条约束怎么共存，没有设计。

## 还差的一层：应用层逻辑不是边界

CC 把最高层策略放在 `/Library/Application Support/ClaudeCode/` 或 `/etc/claude-code/`，
要管理员权限才能写，以普通用户身份跑的 agent 改不动——**靠操作系统的文件权限，
不是靠应用层判断**。再配 `allowManagedPermissionRulesOnly` 取消下层定义规则的资格，
`disableCommandPluginSources` 堵住「用插件绕过策略」这条路（文档原话就是
"Prevents bypassing managed settings"，与发现 09 的结论一字不差）。

我们这一层仍在同一个进程里，属于应用层逻辑。它解决了抢位问题，没有解决
「同进程的东西理论上都能绕」。要补上，得让约束的定义落到 agent 运行身份够不着的地方。
这条没有做，也没有测。
