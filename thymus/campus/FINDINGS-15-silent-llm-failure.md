# 发现 15：模型调用失败不抛错——两侧的兜底都因此失效，网关的 fail-closed 保证被绕过

HANDOFF 从上一轮就挂着「fail-open / fail-closed 路径零失败，没走到过，没有数据」。
用会抛错的假 adapter 直接打，两侧都打。结果比「没数据」严重：**两侧的兜底都是假的**。

测试 `thymus-multiplugin.spec.ts` 论证 34–37，不调真模型，确定性。

## 根因：`ctx.llm.stream` 失败时不抛错

诊断跑出来的实际行为：

```
抛错：没有抛
chunks：[{"type":"finish","reason":{"kind":"error","failure":{"message":"上游炸了"}}}]
```

调用失败时它发一个带错误原因的 `finish` chunk，然后**正常结束迭代**。
`for await` 循环干净地跑完，`try/catch` 一次都不会触发。

## 后果一：插件侧的词表兜底根本不执行

发现 04／05 里模型自己写的语义插件都有这么一段：调模型判定，`catch` 到异常就落回
字面词表。实测这段**永远不会执行**——没有异常可 catch。判定结果为空，插件把原文
原样放出去：

| 输入 | 期望（词表兜底） | 实测 |
|---|---|---|
| 这个不可能 | 这个需进一步确认 | **这个不可能** |
| 这事我管不了 | （词表外，本就漏） | 这事我管不了 |

也就是说：**模型一挂，插件不是退回词表水平，是退回零防护。**

## 后果二：网关的 fail-closed 保证被绕过

发现 10 给网关加了三道保险——约束抛错、超时、返回非法判决，一律按 deny。
但这三道**一道都不会触发**：约束的 `for await` 正常结束，返回 allow，网关如实放行。

我们说过「判不了就不放行」。在这个失败形态下，那句话不成立。

## 修法：判定调用必须走 `judgeText`

`gate.ts` 加了 `judgeText(ctx, options)`：装配文本，并在 `finish.reason.kind !== 'stop'`
时**抛错**，把静默失败翻译成异常。约束改用它之后，网关的第一道保险（抛错→deny）
就接得住了——论证 37 实测 `deny`，理由含「未正常结束」。

规矩：**判定用的模型调用不要直接 `for await ctx.llm.stream`**。

## 这是同一类错误的第三次

- 之前：`say()` 只等 `whenIdle()`，把传输失败读成「模型什么都没做」，测量整个是假的
  （已修，commit `cecf5b9`）。
- 发现 03 二记：三轮反馈有两轮没送达，被读成模型没修好。
- 这次：`ctx.llm.stream` 的失败被读成「判定通过」。

共同形状是：**dsh 用返回值表达失败，而不是异常**；只写 try/catch 的调用方会把失败
当成功。凡是接 dsh 流式接口的地方，都要显式检查结束原因。

## `judgeText` 的覆盖面（论证 38–43）

修法本身也要验，不能假设它管用。dsh 的 finish 有五种结束原因，类型还是
merge-extensible（adapter 能加自己的）。逐种打：

| 结束形态 | judgeText 行为 |
|---|---|
| `stop` | 返回文本 ✓ |
| `max-tokens`（判定被截断，**有文本**） | 抛错——最容易被误当成成功的一种 |
| `aborted` | 抛错 |
| `error` | 抛错，并带上原始失败信息 |
| 根本没有 finish（流干净结束） | 抛错「没有给出结束原因」 |
| adapter 自扩展的未知 kind | 抛错——不认识就不放行 |

`max-tokens` 这条值得单说：判定调用被 token 上限截断时，产出**看起来是正常文本**，
只是判到一半。只看有没有文本的调用方会把它当成有效判定。除 `stop` 外一律不认，
是这里唯一安全的做法。

## 没验的

- 只测了 adapter 层面的失败形态。中途断流（迭代到一半 throw）、畸形 chunk 没测。
- 没测重试：rc.8 把 `DEFAULT_MAX_RETRIES` 从 2 改成 5，本轮诊断 1ms 就返回了错误
  finish，说明这类错误没有走重试，但没有查是哪些错误会重试。
- `judgeText` 只用在网关侧。插件侧要修，得让写插件的一方也知道这个坑——
  而那是提示词的事，本轮没做。
