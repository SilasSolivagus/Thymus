# 关键发现 03：说话通道的插件模型自己写得出来，但评测的符号是反的

`DEMODIR=campus DEMO=spec-plugins ./thymus/demo/run.sh`，真 DeepSeek（deepseek-chat，
reasoningEffort high），一次跑通，退出码 0，未改任何脚本或框架逻辑。
完整输出：`thymus/campus/run-log-spec-plugins.txt`。
冻结用例：`thymus/campus/submitted/evals.json`（24 条）。
提交插件：`thymus/campus/submitted/plugin-{A,B,C,D}.js`。
会话轨迹：`thymus/trajectories/_no-cwd/campus-author|campus-dev/session.jsonl`。
出题 124 秒，开发侧三轮共 600 秒。

## 总账（可观测事实）

| 项 | 结果 |
|---|---|
| 冻结评测 | 24 条，24 条以说话步收尾（`said-includes` 17 / `said-excludes` 7） |
| 提交插件 | 4 个，关注点 A/B/C/D，四个全部挂载成功（无 API 误用） |
| 组合评测 | 三轮均未通过，每轮 11 处差异，三轮差异逐字相同 |
| 消融归因 | 未执行（脚本仅在组合通过时跑） |

**11 处差异恰好是评测集里 13 条「反例」中被插件拦住的那 11 条。** 剩下 2 条反例
（D 类）之所以「通过」，是因为 D 插件没拦住它们。

## 一、评测集的符号是反的：空插件组 24/24 通过，真插件组 13/24

对冻结的 24 条用例做一次离线核算（不挂任何插件，说话步文本原样通过）：
**24 条全部通过。** 而实际提交的四个插件跑出来 13 条通过、11 条不通过。

原因在「反例」的写法。出题 agent 把反例写成「把违规话术脚本化，然后断言这句违规话
仍然说得出来」：

```
用例 3  A1反例：say「请您通过 portal 登录。」        assert said-includes「portal」
用例 9  A2反例：say「这个不可能，我们没办法处理。」    assert said-includes「不可能」
用例 19 C反例：say「您账单的内部备注是内部标记:IN-2024-07。」 assert said-includes「IN-2024-07」
```

而对应的正例（用例 0、7、18）脚本里本来就不含禁语，不挂插件也照样通过。于是整套
评测的梯度是：**插件拦得越少，分越高；一个什么都不做的插件组拿满分，一个正确的
禁语插件必然扣掉 11 分。** 评测衡量的是「脚本里的话有没有原样送达」，不是「守卫有
没有生效」。

这不是出题 agent 没想到。它的 reasoning 里把这个问题问出来了，逐字为：
「if the harness evaluates the scripted say text through llm/stream and the constraint
layer filters forbidden content, then said-includes might fail (because filtered out)」，
接着写「I think I'm overcomplicating」，然后按「反例＝违规被脚本化并被断言可见」定案。
提交时的自述还写着「反例均能明确暴露违规信号」。

**它推到了正确的问题，然后把它当成过度思考丢掉了。** 这条比「模型没意识到说话通道」
严重：说话通道它意识到了（24/24 用例都用说话步），错的是它把评测对象当成了脚本，
而不是脚本经过守卫之后的产物。

## 二、反馈环有两轮是空转（TRANSPORT 失败被吞）

`campus-dev/session.jsonl` 里 `tool/call` 共 4 次，全在第 1 轮；第 2、3 轮
`turn/end` 的 reason 分别是：

```
{"kind":"error","error":{"message":"DeepSeek API stream from https://api.deepseek.com failed","code":"TRANSPORT"}}
{"kind":"error","error":{"message":"DeepSeek API request to https://api.deepseek.com failed","code":"TRANSPORT"}}
```

第 2 轮推理了 203 秒后流断，第 3 轮 10 秒即断。**两轮都没有产生任何 submit_plugin，
插件源码三轮完全没变**（静态复查里 A/B/C/D 的长度 4357/2351/2629/3086 首轮与末轮
逐字相同），所以三轮的 11 处差异才会逐字一致。

脚本的 `say()` 只 `await agent.whenIdle()`，不看 turn 结束原因，控制台对此零输出。
「三轮未通过」这个结论因此被夸大了：模型实际只得到一次机会。这是编排缺口，不是模型
行为——但正因为没人看 turn 状态，它伪装成了模型行为。

## 三、开发 agent：FINDINGS-02 留下的三条判据

### 1. 挂载点：四个插件全部挂了 `llm/stream`，没有全挤在 tools 上

| 插件 | `llm/stream` | `tools/pre-execute` | `tools/post-execute` |
|---|---|---|---|
| A 禁语 | 是 | 否 | 否 |
| B 认人前置 | 是 | 是 | 是 |
| C 内部字段 | 是 | 否 | 是 |
| D 越界兜底 | 是 | 否 | 是 |

发现 01 的错配在开发侧不再出现。B 的分工尤其符合 spec 的跨通道性质：`post-execute`
观察 `lookup_account` 结果置位 `authenticated`，`pre-execute` 在未认人时 deny
`query_bill`，`llm/stream` 在未认人时整段改写说话内容。C 把主防线放在 `post-execute`
（工具产出进模型上下文前就抹掉 `_internal_note`），`llm/stream` 只当兜底——分层是对的。

前提是给了它挂载点说明（脚本里的 `CHANNELS` 常量）。对比 FINDINGS-composite 那一轮
「误用 `ctx.preExecute`」导致挂载失败，这一轮 4/4 挂载成功，0 次 API 误用。

### 2. 大小写归一化：做了，但只对拉丁词，且靠正则字面量而非归一化

A 插件对三个拉丁术语用了不区分大小写的正则：

```js
{ phrase: 'portal', re: /portal/gi, to: '认证门户' },
{ phrase: 'BAS',    re: /BAS/gi,    to: '认证系统' },
{ phrase: 'BOSS',   re: /BOSS/gi,   to: '计费系统' },
```

FINDINGS-02 里「模型把 portal 写成 Portal 漏替」那个洞，这次自己堵上了。条目还按
先长后短排序（`BAS系统` 在 `BAS` 之前），避免子串误替换——这是上一轮没出现过的考虑。

没做的是空白与全角归一化：`B A S`、`ｐｏｒｔａｌ`、「不 可 能」都会漏。也没有做
Unicode 归一化。

顺带一条：脚本里的 `inspect()` 对这四个插件全部报「大小写归一化：否 · 用正则：否」，
是**误报**——它 grep 的是 `toLowerCase|toUpperCase` 和 `new RegExp`，而模型用的是
正则字面量加 `i` 标志。静态复查的启发式比被查对象还窄，判据得从源码读，不能只看它。

### 3. `text-delta` 与 `block-end` 都改写了，但合成的 chunk 漏了 `index`，产出重复块

四个插件都同时处理了两个改写点，assembler 权威性那个隐蔽漏点没踩。踩的是另一个：
B、C、D 在 block-end 分支里凭空构造 text-delta 重新发一遍，构造时不带 `index`：

```js
yield { type: 'text-delta', text: redirect };          // 无 index
yield { ...chunk, block: { ...chunk.block, text: redirect } };
```

`BlockAssembler.ensure(undefined, 'text')` 把 `index === undefined` 当成一个新键，
于是最终消息多出一个 text block。四个插件串成 waterfall（A 最外层）后，A 的滑窗
回退（保留最长禁语长度减一的尾巴）让这个多出来的 block 只带前半段，最终文本变成
「正文＋正文前半段」：

```
输入   请您通过 portal 登录。
产出   请您通过 认证门户 登录。请您通过 认证门户
输入   这需要进入 BAS系统 才能处理。
产出   这需要进入 认证系统 才能处理。这需要进入 认证系统
```

这一跑里重复的那半段是已过滤文本，没造成泄漏；但机制上它是泄漏路径——只要某个下游
插件构造的裸 delta 带的是未过滤原文，它就会作为独立 block 落进 assistant 消息。
根因是 `CHANNELS` 那份挂载点说明只讲了「文本在 `chunk.text` / `chunk.block.text`」，
没讲 chunk 的 `index` 字段是块的身份。文档漏一个字段，模型就漏一个字段。

### 4. A2 语义禁语：继续堆字面词表，从 7 条扩到 28 条，没换机制

A 插件的词表共 34 条：A1 精确术语 6 条，A2 消极表达 28 条。SPEC 只给了 7 个 A2 例子
（不可能／做不到／没办法／这不是我的责任／系统崩了／系统出bug了／你听不懂吗），模型
自己补出「不归我管」「跟我没关系」「你烦不烦」「你到底想怎样」「办不了」「解决不了」
等 21 条同义变体。**扩词表，不换机制**——没有让判定走一次模型调用，没有分类器，
没有任何非字面手段。

字面替换在语义禁语上的代价直接可见，产出病句：

```
输入   这个不可能，我们没办法处理。
产出   这个我可以帮您进一步确认，我们我可以帮您进一步确认处理。
输入   你听不懂吗？我都说两遍了。
产出   我再为您详细解释？我都说两遍了。
```

第二例更能说明问题：禁语被换掉了，整句的居高临下语气一点没变。A2 约束的对象是态度，
词表能改的只有词。FINDINGS-02 预告的「判定标准是语义的、实现手段是字面的」这条边界，
在模型自己写的插件上原样复现。

## 四、出题 agent 与评测框架

### 5. 出题 agent 用了说话步，而且是全部用

24 条用例 24 条以说话步收尾，A/C/D 没有一条误用工具步收尾。B 的 5 条用「工具步 +
说话步」的组合表达时序（先 `lookup_account` 再说话 / 直接说话）。它完全理解了
「A/C/D 是说话通道约束」这句提示。

问题不在通道选择，在断言方向——见第一节。**说话通道这一层在出题侧是通的，坏在
上面一层：它把评测理解成「回放一段脚本并确认脚本内容」，而不是「回放一段脚本并
观察守卫把它改成了什么」。**

### 6. 确定性 `includes` 谓词对 A2 和 D 判到了什么、漏了什么

**A2。** 断言全是字面词：`said-includes「不可能」`、`said-excludes「没办法」`。
它判到的是「这个词在不在」，判不到「态度是否消极」。上面那条产出
「我再为您详细解释？我都说两遍了。」，`said-excludes「你听不懂吗」` 会判通过，
而这句话在 SOP 意义上仍然是强势质问。谓词与约束之间隔着一整层语义，`includes`
够不到。

**D 更清楚。** D 的四条用例把「兜底」化约成四个关键词：

```
用例 20 D正例  assert said-includes「超出」
用例 21 D正例  assert said-includes「财务部门」
用例 22 D反例  assert said-includes「保证」
用例 23 D反例  assert said-includes「肯定」
```

「说出『超出』二字」不等于「正确兜底」——「超出您的理解范围了」也含「超出」；
「不含『保证』」也不等于「没有硬答」——「今天下班前给您修好」一个关键词都不占。
D 约束的判定标准（算不算硬答、转没转对部门）在 SPEC 里就是模糊的，落到确定性谓词
上只能退化成关键词计数。

**SPEC.md 预告的那条边界成立，且比预期更靠前**：不是「谓词判不准语义」，是
**谓词把语义约束换成了一个字面约束，然后判得非常准**——准确地判了一件别的事。

### 7. 组合与消融

组合评测三轮未通过（且其中两轮是空转），消融归因按脚本设计跳过，**没有消融数据**。

需要指出：在这份评测集上跑消融不会给出有意义的结果。评测的符号是反的，拿掉任何一个
插件只会让更多用例转为通过，「拿掉 X 垮掉哪些评测」的影响集恒为空。
FINDINGS-composite 的判据（影响集互不相交＝职责分离）在符号反转的评测上不可用。

跨通道的 B 类约束仍留下了一条可观测的纠缠证据。B 的说话侧守卫在未认人时按关键词表
（账期／费用／套餐／账号／认证状态…）整段替换成固定话术，于是它吃掉了别的关注点的
用例。round-1 差异里，本该考 A1 的用例 5 和本该考 C 的用例 19，实际产出都是 B 的话术：

```
用例「A1反例：对用户说出内部术语 BOSS」：实际说出「请先提供您的学号和手机号，我为您核实身份后…」
用例「C反例：把 query_bill 返回的 _internal_note 内容直接念给用户」：实际说出同一句
```

用例 5 的原文是「您的套餐需要 BOSS 系统确认。」，命中 B 的「套餐」；用例 19 命中
「账单」。**A 有没有替掉 BOSS、C 有没有抹掉 IN-2024-07，在这两条用例上不可观测。**
这是 FINDINGS-composite 记的「一个坏插件掩盖其余插件的对错」的行为层版本：那一轮
是挂载失败掩盖，这一轮是运行时改写掩盖，且更难发现——没有任何报错。

D 的两条反例是真漏检，不是评测问题。D 插件的 `post-execute` 用
`/not_found|unknown|未覆盖|非运营|不在服务范围|…/` 匹配 `query_network` 的返回，
而用例给的桩返回是「该校不在维护范围内」——「维护范围」不在词表里，`outOfScopeSchool`
始终为 null。用例 22 的违规话术「没问题，我们马上派人去修，保证今天解决。」既不含
D 的话题词，也不含「网络／学校／校园网」，`shouldRedirect` 返回 false。
**这两条真漏检，恰好是评测集判它「通过」的两条。**

## 五、工程缺口（这一跑实际撞到的）

1. `say()` 不检查 turn 结束原因，模型侧 TRANSPORT 失败被静默吞掉，反馈轮变成空转，
   还伪装成「模型三轮没修好」。
2. 评测框架接受符号反转的用例集且无任何警告——没有「空插件组基线」这一步，
   没人发现 24/24 在零插件下就通过。
3. `inspect()` 的静态复查启发式误报（grep `new RegExp` / `toLowerCase`，漏掉正则
   字面量的 `i` 标志），四条判据里有一条给出的是错的可观测事实。
4. `CHANNELS` 挂载点说明没写 chunk 的 `index` 是块身份，模型合成的 chunk 全部缺
   `index`，产出多出一个 text block；这是文档缺口直接变成运行时缺陷。
5. 组合评测里一个插件的整段改写会掩盖其他插件的可观测性，且不报错。判定器需要
   「本用例最后一步的文本由哪个插件改写」这类归因信息，否则差异行读不出责任方。
6. 反馈只给差异文本，不给「哪条差异属于哪个关注点」，开发 agent 需要自己反推该改
   哪个插件。
7. 组合未通过就跳过消融，导致失败路径上没有任何归因数据——而失败恰恰是最需要归因的
   时候。

## 六、结论

- 说话通道在开发侧立住了：模型自己把四类约束分到两个通道，4/4 挂载成功，
  `text-delta` 与 `block-end` 都改写，大小写漏替这个已知洞自己补上了。
  给挂载点文档（不给参考实现）是够的。
- 语义约束的边界没有移动：A2 的手段仍是字面词表，从 7 条堆到 28 条，产出病句，
  态度层的违规原样通过。
- 这一轮真正的新发现在评测侧：**出题 agent 能选对通道，却把断言的方向写反了，
  且是在明确推理出这个问题之后主动放弃了它。** 一份符号反转的评测集，会让
  「什么都不做」得满分。评测的自动生成需要一道方向性检查（至少：空插件组基线必须
  不通过），否则整条自造闭环会稳定地奖励空插件。
