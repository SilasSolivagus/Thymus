# 发现 21：SPEC.md 整份编译成声明——填得满四分之三，措辞是未受控变量

本轮命题的收口：**过去要人写的客服插件，能不能换成一份声明**。
`spec-declarations.ts` 把 SPEC.md 整份写成 6 条声明（D 按发现 20 拆成两条），
`check-spec-full.ts` 跑验收，真 DeepSeek，3 轮。完整输出在 `run-log-spec-full.txt`。

## 一、填得满吗

| SPEC 条款 | 声明 | 结果 |
|---|---|---|
| A1 精确内部术语 | `forbidden-phrases` | 填得进 |
| A2 语义消极表达 | `semantic-policy` | 填得进 |
| B 认人前置 | `require-before` | **只填了一半** |
| C 内部字段不外泄 | `no-leak` | 填得进 |
| D 越界兜底 | `require-fallback` + `semantic-policy` | 填得进，但要拆成两条 |
| 会话现实三条 | —— | **填不进，也不该填** |

三条填不进去的，`UNCOVERED` 里逐条写了理由：

- **B 的说话那一侧**。原文管的是「未认人不得 reply 账号相关内容」，内置类型只能按
  工具名判前置，判不了「这段话是不是在讲账号详情」。声明做到的是「未认人不得取数据」，
  说话那一侧靠的是 C 类同一个道理——拿不到就说不出来。要真表达它，需要一个把 B 的
  事实来源（会话日志）和 D 的上下文判定合起来的新类型。**这是「该补哪个内置类型」的
  信号，本轮不补，先记着。**
- **会话现实三条**（槽位多轮追问、信息不全不得直接查、闲聊不得误调工具）。这三条是对
  能力的要求，不是约束——没有「违反」的那一刻可以拦。约束层管不了，该由评测集去测。
- **A2 与 D 的判定标准本身是模糊的**（SPEC 自己写了这句）。声明写得出来，判得准不准
  是判定器的事。

## 二、验收结果（3 轮）

| 声明 | 必拦 | 必放 | 留出 |
|---|---|---|---|
| A1 内部术语（字面词表） | 3/3 3/3 3/3 | 2/2 ×3 | **0/2 0/2 0/2** |
| A2 服务禁语（语义） | 3/3 ×3 | 2/2 ×3 | 3/3 2/3 3/3 |
| B 认人前置（白名单） | 2/2 ×3 | 4/4 ×3 | 1/1 ×3 |
| C 内部字段（抹除） | 1/1 ×3 | 1/1 ×3 | （没写） |
| D 越界兜底 | **0/1 1/1 0/1** | 2/2 ×3 | 2/2 ×3 |
| D2 不得承诺（语义） | 3/3 3/3 2/3 | 2/2 ×3 | 2/2 ×3 |

三件事值得单说：

**A1 的留出集稳定全漏（0/2×3）。** 这不是声明写错了，是字面词表的能力边界——
「请登录后台管理系统查询」「这条在计费系统里能查到」跟词表一个字都不重叠。
数字摆在那儿就是这个类型的诊断书：**这条该并挂一条 `semantic-policy`**。
按设计留出集不计入 `ok`，所以它照样报 ✓——这正是留出集与必拦必放分开计的用处。

**C 类没有留出集。** 我没写出来：这一类的「同类但没列出」是别的内部字段，
要枚举字段才写得出题，而按值匹配已被证明失灵（发现 16）。留白，不假装有。

**D 的必拦不稳（[0,1,0]）**，而单独跑 D 时（发现 20，11 轮）「非运营学校」那一类
一条没漏过。两处唯一的差别是 `fallback` 的措辞——见下。

## 三、措辞消融：半句无关的话，改变判定结果

同一条 D，只改 `fallback` 一处，同一批用例，各 3 轮：

| `fallback` 措辞 | 必拦 |
|---|---|
| `不得硬答或承诺，必须说明超出范围或权限并转相关部门` | 1/1 1/1 1/1 |
| `说明超出范围或权限，并转相关部门` | 1/1 **0/1** 1/1 |

把整份 SPEC 那一轮的 `[0,1,0]` 并进来，「只讲转出」这个写法 6 轮里漏了 3 次，
「带那半句」的写法 3 轮全中（加上发现 20 完整臂的 11 轮，那一类一条没漏过）。

要命的是，那半句「不得硬答或承诺」在拆开写之后**本来就该删**——它属于另一条约束
（D2）。删掉它逻辑上更干净，判定结果却更差。判定器不是只读条款的语义，它也被措辞的
强度影响。

样本小（各 3 轮），方向一致但没坐实。记下来的是现象和它的含义，不是一个系数。

## 结论：这条路成立，但不是「填表就完事」

- **四类里三类填得满，B 填了一半，会话现实那三条根本不属于约束层。**
  就交付形态而言，「客服插件换成一份声明」成立。
- **代价是措辞进入了结果。** 同一条规矩、同一个模型、同一批用例，声明里一句话的
  取舍就能改变判定。而措辞本身没有验收机制——你只能靠跑留出集发现它不好。
- 所以交付形态不是填表，是**填表 + 跑一遍留出集 + 看数字调措辞**。留出集在这里第三次
  证明了自己是唯一有判别力的一层：A1 靠它暴露能力边界，D 靠它暴露拆分收益，
  措辞消融也只有它和必拦两组能看出来。
