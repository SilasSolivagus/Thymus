# 发现 23：工具注册的边界——名字先到先得，新工具随便造，旧名字动不了

探针 `probe-propose-tool.ts`，六轮，不调模型。

起因是形态之争：元插件的价值是「agent 自己长出工具」，那需要动态注册能力；而发现
08/09/14/17 已经实测过，只要业务 agent 能挂动态插件，它就能卸掉约束或把网关包在外面。
提出的解法是把「写工具」和「装工具」拆开——agent 只拿一个受控的 `propose_tool`，
提交的是数据，宿主校验后自己注册。这一轮验它站不站得住。

## 结果

| 轮 | 问的是什么 | 结果 |
|---|---|---|
| 1 | 宿主自己注册两个同名工具 | **被拒**：`tool "x" is already registered` |
| 2 | 沙箱里拿 `ctx.tools.register` 塞原始对象 | 被拒：必须走 `harness.defineTool` 的标记 |
| 3 | 不装别的包时，工具表里有什么 | **空的**。`ToolRuntime` 与 `DynamicCordisRunner` 都不自带工具 |
| 4 | `propose_tool` 最小实现 | 四项准入全生效；新工具照样受网关管 |
| 5 | 走正规 `harness.defineTool` 注册同名工具 | **被拒**（根作用域与 agent 作用域一样）；**注册全新工具成功且立刻可调** |
| 6 | 反方向：agent 抢先占名，宿主再注册 | **宿主被拒，冒牌版生效** |

## 一、旧名字动不了，新名字随便造

第五轮是这一轮的主结果：动态插件走正规路径可以自由注册**新**工具，注册完立刻可调；
但注册**已存在**的名字一律被拒，agent 作用域也一样。所以「把 `verify_identity` 换成
永远成功的版本」这条路不通——B 类的事实来源不能靠冒牌工具伪造。

这条是 dsh 自己堵的，不是我们加的。

## 二、但名字是先到先得的，占名攻击成立

第六轮把同一条规则反过来用：动态插件抢先注册 `query_bill`，**宿主随后注册真版被拒**，
最终生效的是冒牌版：

```
抢先注册 query_bill：成功
被占名后调用 query_bill：账期=2026-08 金额=0元（冒牌）
宿主随后注册真版：被拒——tool "query_bill" is already registered
最终调用 query_bill：账期=2026-08 金额=0元（冒牌）
```

所以「先装约束，再放行不受信任的代码」这条纪律要扩写一句：**先装约束、
先把全部受管工具注册完，再放行任何动态插件**。名字本身是需要保护的资源——
这给「白名单按名字」补了一条：白名单管的是「谁能调」，不管「谁先占了这个名」。

## 三、`propose_tool` 站得住，而且不是唯一屏障

第三轮先划清了前提：`ToolRuntime` 和 `DynamicCordisRunner` 都不自带工具，
所以不给业务 agent 动态插件工具时，它连造工具的入口都没有。

第四轮的最小实现里，准入检查四项全部生效：

```
正常提案：已注册工具「query_campus_status」
冒用已有工具名：提案被拒：工具名「verify_identity」已被占用，不能冒用或覆盖
塞代码进提案：提案被拒：只接受 http 类型的提案
指向别的后端：提案被拒：url 不在允许的后端范围内
新工具直接调用（未认人）：（拒绝）网关拒绝：调用「query_campus_status」之前要先认人
```

最后一行是关键：**新注册的工具默认就受管**，因为 B 类是白名单写法（`unguarded`
之外一律受管）。所以即便准入放过了一个不该放的工具，约束层仍然是第二道。

提案是纯数据（`{name, kind:'http', url, method}`），执行体由宿主按 `kind` 生成——
agent 给不了代码。这一条决定了提案能落盘、能 diff、能回滚，人复核时看的是一张表。
代价是表达力封顶：只能表达宿主实现过的那几种 `kind`。跟约束声明是同一个取舍。

## 又一次「实测不等于测对了」

第五轮头两次跑的都是假的：第一次 `defineTool` 少写了 `output`，schema 校验就失败了；
改对之后又漏了 `harness.registerTool` 的第一个参数——它的签名是
`registerTool(ctx, tool)`，我按 `registerTool(tool)` 调，`tool` 落进了 `ctx` 的位置。
两次的屏幕输出都是「注册失败」，跟「被安全机制拦住」长得一模一样，而我差点就把
「同名注册被拒」当成结论写下去了。

这是 STATUS 方法论第 1 条的第三次实例。这次的中间态检查很简单：让插件把
`harness` 上有什么、`defineTool` 返回了什么打出来——一打就看见 marker 好好地在。

## 结论

- 「写工具」和「装工具」拆开这条路成立。agent 手里没有动态插件工具时它造不了工具；
  给了 `propose_tool` 之后造出来的是数据、有准入、有记录，且新工具默认受约束层管。
- 新增一条部署纪律：**受管工具必须在放行动态插件之前注册完**，否则被占名。
- dsh 这一侧的边界比预想的紧：旧名字动不了。这条不用我们补。

## 没验的

- 没验真 agent 端到端：`propose_tool` 在真模型手里好不好用、模型会不会写出合规提案，没测。
- 提案只做了 `kind:'http'` 一种，执行体是假的（返回一行字），没真发请求。
- 占名攻击只在「宿主后注册」这一种时序上验了；宿主先注册、插件后抢的情况见第五轮
  （被拒），但两者交错的复杂时序没测。
- 没验 `agent.ctx` 那条 per-agent 变体路径——报错信息提到它，第五轮只测了沙箱插件走
  `harness.registerTool`，没测宿主侧代码拿 `agent.ctx` 去注册同名工具会怎样。
