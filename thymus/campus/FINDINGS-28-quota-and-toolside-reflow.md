# 发现 28：配额上限验到了，去重没有——以及回流补上工具侧

两件收尾，都是发现 24/25 留下的欠账。

## 一、注册数上限：真链路验到了

发现 25 里配额一次都没触发，因为那几轮模型没有反复造工具。这一轮换了个**自然会撞上**
的任务，不靠逼它绕过：用户一次问三件事（校区网络、缴费方式、报修进度），每件都要一个
新工具，而上限设成 2。

```
3/3 轮：提案 3 次，注册 2 个，第 3 次被配额拒
拒绝理由：本次会话注册的工具已达上限（2 个）：campus_network_status、payment_methods。
          先用已有的工具，或换个思路。
```

理由里带上已注册的工具名是有意的——被拒时模型需要知道手上有什么。三轮它都接着用已有
的两个工具答了前两问，第三问如实说没查到。

## 二、去重：两次设计都没造出那个局面，仍然只有单测

第一次（发现 25）模型只提了 1 次案，没机会重复。这一轮换了个思路：让新工具的后端返回
`503`，指望它换个名字重提同一个后端——**结果它重试的是同一个工具**：

```
3/3 轮：提案 1 次，注册 1 个，去重拒 0 次
新工具被调用：campus_network_status, campus_network_status   ← 同一个工具调了两次
```

这是个有信息量的负结果：**后端报错时模型的第一反应是重试，不是换工具**。
所以我原来设想的触发路径不成立。

去重真正出现过的场景只有一次——发现 24 臂 C：被网关拦住之后一口气注册 4 个工具，
其中两个的 url 完全相同。那个行为本身不稳定（后来两次重跑都没复现）。

**结论：注册数上限有真链路证据，去重没有，只有单测（论证116、117）撑着。**
不再继续换场景去钓——那正好是这轮刚写的模块在防的事（反复重抽直到满意）。

## 三、探针自身的一个缺陷，记下来

探针里所有提案出来的工具共用一个桩返回值，于是模型查缴费方式时拿到的是网络故障的
文本。它当场识破了：

> 我查询缴费方式时，系统返回的却是"长安校区核心交换机故障"的信息，与缴费方式无关。
> 可能是后台数据接口暂时错乱。

不影响配额那条结论（配额在工具执行之前就生效了），但**它确实影响了回答质量**，
而我一开始没想到。桩要按工具名分开返回。

## 四、回流补上工具侧

原先 `BadCase` 只有一个 `say` 字段，只装得下说话类样本。现在样本是个联合类型，
五种声明各有各的形状：

| `sample.kind` | 对应声明 | 载荷 |
|---|---|---|
| `say` | `forbidden-phrases` / `semantic-policy` | 一句话 |
| `fact-say` | `require-before-say` | 会话事实 + 一句话 |
| `dialogue` | `require-fallback` | 用户问 + agent 答 |
| `tool-output` | `no-leak` | 工具产出原文 |
| `tool-call` | `require-before` | 已成立的事实 + 这次调用 |

两处细节值得说：

- **`tool-call` 的事实是集合，`before` 先排序再算身份**。不排序的话，同一条样本换个
  记录顺序就会落到另一侧，分流的确定性就没了（论证141c）。
- **形状对不上的样本不硬并，而且会报出来**（`ApplyResult.skipped`）。归错约束、
  约束名写错、通道不对，都落到这里。静默丢弃在这一层是最糟的失败方式——样本没了，
  而评测集看着照样是绿的（论证140、141a）。

## 没验的

- 去重在真链路上仍无证据。
- 回流的样本目前靠人手填，没有从会话日志里自动摘出候选的工具。
- 只验了并入与分流，没验「并入之后跑一遍评测、与上一版比」的完整一轮。
