# 发现 13：两个语义插件挂一起会无限递归——多插件不是模型能力问题，是机制问题

HANDOFF「已知未解」的第一条：`llm/stream` 上「对用户说的话」和「判定协议」是同一条
通道，多插件下会互相污染。发现 04 组四见过一次，之后一直没正面测。现在测了，
结论比「污染」严重。

测试 `thymus-multiplugin.spec.ts`（论证 16–19），全程假 adapter，不调模型，确定性。
假 adapter 把收到的文本回显成 `[JUDGED]<原文>`，所以从产出能直接读出谁判了谁。

## 现象：一句话，12 次判定调用

两个插件各自在 `llm/stream` 里再调一次模型做判定（就是发现 04 那种语义约束），
每个的防递归都只认得**自己**创建的 options 对象——这是人手写的那版做法，没有偷懒。

第一版测试**直接挂死**。加了深度上限才跑得完，上限本身就是证据。

用户说一句「您好」，深度上限 3 时：

```
判定调用 12 次，前两次是：
  第 1 次：<B>您好                    ← 只有这次判的是用户原话
  第 2 次：<A>[JUDGED]<B>您好         ← A 把 B 的判定调用当成了「要说的话」
  …往后每次的输入里都嵌着上一次的判定输出

用户最终看到：12 层嵌套的 [JUDGED] 标记，原话「您好」埋在最里面
```

原因是结构性的：B 发起的判定调用同样走 `llm/stream` waterfall，撞进 A 的 handler；
A 的防递归表里没有 B 的 options，于是 A 把它当成用户正文判定并改写；A 的这次判定
调用又撞进 B 的 handler……**两个都写对了自己那部分，合起来仍然不收敛。**

## 结论：这一类多插件失败与模型能力无关

之前把「多插件同时正确从未通过」记成模型能力边界。这一轮说明，**至少语义约束这一类，
问题在机制**：即便两个插件都由人手写、防递归都写对，挂在一起也是坏的。
再强的模型也写不出「在这条通道上与任意其他语义插件共存」的插件——
它没有能力知道别人的调用是不是判定协议。

## 构造性的另一半：判定放进网关就不互相污染

同样两条语义约束，改成网关里的 `Constraint`（裁决发生在整条 waterfall 跑完之后），
不挂任何 `llm/stream` 插件：

```
判定调用 2 次：<A>您好 与 <B>您好      ← 各判一次，判的都是用户原话
用户正文：您好                          ← 没被判定协议碰过
```

原因也简单：网关的判定调用照样走 `llm/stream`，但那条链上没有别的 handler，
谁也拦不到谁。**语义判定应该在网关里做，不是在插件里做。**

顺带：污染发生时网关照样拦得住——论证 18 里一条「判定协议不得出现在正文」的
网关约束把那 12 层嵌套判为 deny。

## 边界

- 只测了两个插件、只测了语义判定这一类。字面词表插件之间不互相调用，不受此限。
- 深度上限 3 是为了让现象可观测，不是修法。真实部署里没有这个上限。
- 「判定放网关」解决的是插件之间的污染，没有解决「多个网关约束彼此的代价叠加」——
  两条约束就是两次模型调用，串行，延迟翻倍。没测。
- 模型能不能一次写对多个插件（能力那一半）仍未验证。但按本轮结论，
  语义约束这一类**不该再让它写成插件**，所以那个问题的形态变了。
