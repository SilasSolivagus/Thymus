# 实跑记录：一个目标 → 一组插件

`DEMO=spec-composite ./thymus/demo/run.sh`（真 DeepSeek）
+ `thymus-composite.spec.ts`（确定性证明框架能力）。

一个 spec 含三条关注点：删除保护(a) / 危险操作确认(b) / 输出脱敏(c)。
开发 agent 可多次 submit_plugin，自主决定拆几个。

## 架构能力：已确定性证成

用手写的三个正确插件（各司一条关注点），证明了框架的两项能力：

1. **组合评测**：三个插件挂进同一运行时，7 条评测全部通过——它们通过 waterfall
   共存，各自只拦自己的工具、其余 next() 放行，不互相拆台。

2. **消融归因**：逐个拿掉一个插件重跑——
   - 拿掉删除守卫 → 只有 a 的评测垮掉
   - 拿掉确认守卫 → 只有 b 的评测垮掉
   - 拿掉脱敏 → 只有 c 的评测垮掉
   三个影响集互不相交。

**「拿掉 X 只垮 X 的评测」= 职责真正分离的判据**，可计算。这是 DESIGN.md 5.3
贡献度分配第一次在真实多插件上落地——之前单插件用不上消融。反过来，若拿掉某插件
垮掉的评测跨越多个关注点，即为职责纠缠，应拆。消融把「拆得对不对」变成可判定的。

## 真实 agent 跑出的两个发现

**发现一：拆分决策，agent 自己做对了。** 只说「按单一职责拆」，DeepSeek 就把三条
关注点拆成三个插件（concern a/b/c），拆分粒度正确。「一个目标可对应多个插件」不仅
技术可行，agent 也能自主完成拆分。

**发现二：多插件同时正确，对当前模型是真难点。** 单插件时每档一轮即过（见
FINDINGS-spec-tiers）；三条关注点同时上、还要拆成三个插件后，DeepSeek 三轮未能
让三个插件同时正确——它在 API 细节上出错（如误用 ctx.preExecute 而非
ctx.on('tools/pre-execute')）。任务复杂度上升后，开发方的正确率显著下降。这不是
框架问题，是模型能力边界，且指向一个产品含义：多插件场景需要更强的开发侧脚手架
（API 校验、单插件先过再组合、失败定位到具体插件）。

## 编排缺陷（已修）与由此暴露的真问题

初版反馈把「修正插件」实现成累加，导致插件越修越多（3→6→9），旧错版本与新版本
混在一起。**这半是 bug（追加而非替换），半是真问题**：多插件下「修正」必须能定位
到「替换哪一个」。

修法同时回答了这个真问题：以 concern（关注点）为键——同一关注点重复提交＝替换，
不同＝新增。多插件的版本管理需要一个稳定的身份键，concern 就是它。

## 判定器一个已知弱点

组内任一插件挂载失败（如用错 API），当前 runCase 对整组所有评测报同一个挂载错误，
**一个坏插件掩盖其余插件的对错**。这对「组合部署」是真实的（一个坏器官确实拖垮
整组），但对开发反馈不利——无法告诉开发方「你的另外两个插件其实是对的」。
改进方向：挂载失败按插件隔离报告，或强制「单插件各自先过评测子集，再组合」。

## 结论

- 框架层面：一个目标 → 一组插件，组合评测与消融归因均成立且可计算。项目从
  「器官的生命周期管理」推进到「器官组合的生命周期管理」，这一层的机制立住了。
- 模型层面：拆分决策 agent 能做；多插件同时正确是当前能力边界，需开发侧脚手架。
- 已定位两处工程缺口：多插件版本管理需身份键（已解决＝concern 键）；判定器挂载
  失败需按插件隔离（未解决）。
