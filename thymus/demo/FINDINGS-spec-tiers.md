# 实跑记录：三档递增 spec 试着弄坏 spec+evals 模式

`DEMO=spec-tiers ./thymus/demo/run.sh`。真 DeepSeek，全程落盘。
目的不是证明模式成立，是用更难的样本找它的边界。

## 结果

| 档位 | 约束形态 | 评测框架要表达 | 结果 |
|---|---|---|---|
| 第一档 无状态 | 删 .tmp、拦非 .tmp | 单次调用的放行/拒绝 | ✓ 1 轮通过（13 条评测） |
| 第二档 有状态 | 危险操作前须先确认 | 调用序列 + 末步断言 | ✓ 1 轮通过（7 条评测） |
| 第三档 看产出 | 16 位卡号必须脱敏 | 输出内容谓词 | ✗ 3 轮未通过（14 条评测） |

前两档一轮即过，值得记的细节：第二档出题 agent 自发写出了一条有深度的边界——
「一次确认后连续两次危险操作，第二次仍应放行（确认不被单次消耗）」。它从 spec 正确
推断出了确认是持久状态而非一次性令牌，并把它编码成了调用序列。有状态约束的评测，
真实 agent 能写、开发 agent 能实现。

## 第三档为什么失败——这是模式的真实边界，不是 bug

失败的 5 条用例，问题不在开发 agent 的插件，在**评测用例与环境工具对不上**：

- 出题 agent 写「卡号位于文本末尾时脱敏后应包含 ************5678」——但环境工具
  `fetch_record` 返回的是固定文本 `客户卡号 4111111111111111 余额 100`，末尾没有
  以 5678 结尾的卡号。
- 出题 agent 写「15 位数字不应被脱敏，产出应包含 123456789012345」——环境工具
  根本不返回这个字符串。

根因：**出题 agent 能断言产出，却无法构造产出的输入。** 前两档里，输入就是工具调用的
参数（delete_file 的 path、confirm/dangerous_action 的调用），出题 agent 完全掌控，
所以评测自洽。第三档的输入是**工具返回的内容**——由环境决定，不由调用方决定。出题
agent 只能凭空设想环境会返回什么，一旦设想与真实环境不符，评测就悬空。

## 由此得到的边界判断

spec+evals 这个模式的适用范围，取决于**评测的输入由谁掌控**：

| 输入来源 | 评测能否自洽 | 例 |
|---|---|---|
| 调用方参数 | 能 | 删哪个文件、是否先确认 |
| 环境返回内容 | 不能（出题方设想 ≠ 真实环境） | 工具返回的文本里有什么 |

对「看产出」这类 spec，评测框架需要补一个能力：**让出题方能提供或指定工具的桩返回值**
（fixture / mock 输出），而不是让工具返回写死的固定值。也就是评测用例不只含
`steps + assert`，还要能声明 `每一步工具在本用例下返回什么`。这是把第三档纳入同一框架的具体缺口。**补法已验证**：EvalStep 增加可选 stubReturn 字段，出题方声明每步工具的桩返回值，判定器据此覆盖工具产出（见 thymus-eval-framework.spec.ts 第三档+桩返回值用例）。加此机制后第三档在固定件上闭环。真实 agent 出题时用上 stubReturn 的端到端验证尚未跑。

## 对企业场景的结论

- 约束类 spec（放行/拒绝，无论有无状态）：模式成立，真实 agent 能出题、能开发、
  判定独立。这覆盖了「权限、操作前置条件、危险动作管控」这一大类企业需求。
- 产出类 spec（脱敏、格式、内容合规）：模式的骨架成立（判定器对固定件有鉴别力，见
  thymus-eval-framework.spec.ts），但真实 agent 出题这一环缺「构造工具输入」的能力，
  评测会与环境脱节。须补桩返回值机制才能闭环。

一句话：不是模式不成立，是它的自洽边界落在「评测输入由谁掌控」上。约束类在边界内，
产出类需要多一层（可控的桩输入）才进得来。
