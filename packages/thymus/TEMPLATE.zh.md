# 填表工作单

把一份 SOP 变成可交付的约束声明。照着填，填完跑两个命令。

**这份工作单只覆盖人不可替代的那几件事**：写留出用例、把混在一起的条款拆开、
判定「这条表达不了」、调措辞。其余的机器都能查——所以每一节末尾都有一句
「机器会替你查什么」，凡是机器能查的，你不用逐条自检。

---

## 第 0 步：先通读 SOP，逐条打三种标记

| 标记 | 含义 | 去向 |
|---|---|---|
| **能列举** | 不许说的话/词能精确列出来 | `forbidden-phrases` |
| **没边界** | 只能用一句话描述，举得出例子但列不全 | `semantic-policy` |
| **有前置** | 做某件事之前必须先做过另一件事 | `require-before` |
| **不外泄** | 某个工具的产出里有不能给用户看的字段 | `no-leak` |
| **越界转出** | 问到管不了的事，必须说明并转出 | `require-fallback` |
| **表达不了** | 上面五种都套不上 | 写进 `uncovered`，**不要硬套** |

> **一条 SOP 条款不等于一条声明。** 条款里同时出现「什么时候必须做什么」和
> 「什么时候都不许做什么」时，拆成两条：前者是有条件的义务，后者是无条件的禁止。
> 写成一条会让无条件那半被有条件那半吃掉——实测过：不拆时留出集 3–4/5，拆开后 5/5。
>
> *机器会替你查什么*：一条声明的文本里同时出现「必须/应当」和「不得/禁止」时会提示拆。

## 第 1 步：逐条填声明

### `forbidden-phrases` — 能列举的禁语

```ts
{
  name: '内部术语不外泄',
  type: 'forbidden-phrases',
  phrases: ['portal', 'BAS', 'BOSS', '工单退回'],
  ignoreCase: true,          // 缺省开。SOP 里的术语常有大小写变体
  evals: { deny: [...], allow: [...], heldout: [...] },
}
```

**这个类型的留出集必漏，这是它的能力边界，不是你写错了。** 报告里那个 0/N 就是
「该不该并挂一条 `semantic-policy`」的依据。

### `semantic-policy` — 没有精确边界的规矩

```ts
{
  name: '服务禁语',
  type: 'semantic-policy',
  policy: '不得出现态度消极、强势质问、甩锅推诿的表达，如「不可能」「做不到」等。',
  provider: 'deepseek-official', model: 'deepseek-chat',
  evals: { deny: [...], allow: [...], heldout: [...] },
}
```

`policy` **尽量照抄条款原文**，不要为了好判而改写。改写之后你验收的就不是 SOP 了。

### `require-before` — 前置条件

```ts
{
  name: '认人前置',
  requires: 'lookup_account',        // 它成功调用过之后，受管工具才放行
  unguarded: ['query_network'],      // 不需要前置的工具。其余一律受管
  type: 'require-before',
  evals: { deny: [...], allow: [...], heldout: [...] },
}
```

**按白名单写**：列的是不需要前置的工具。反过来列受管工具是黑名单，新工具默认在管辖
之外——实测过，agent 被拦住之后会连造几个新工具试图绕过，白名单挡住了，黑名单挡不住。
`requires` 自己永远免检，不用写进 `unguarded`。

### `require-before-say` — 说到某类内容之前必须先有某个事实

```ts
{
  name: '认人后才能答账号问题',
  type: 'require-before-say',
  requires: 'lookup_account',                 // 会话事实：这个工具成功调用过
  topic: '具体账号的账期、费用、账号详情',      // 什么算受限，照抄条款
  reply: '麻烦您先提供一下学号、手机号码，这边为您查询。',
  provider: 'deepseek-official', model: 'deepseek-chat',
  evals: { deny: [...], allow: [...], heldout: [...] },   // 每条是 { before, say }
}
```

**跟 `require-before` 配成一对用**：那条拦「不许去查」，这条拦「不许说出来」。
只写一条就只覆盖一侧——光拦住取数据，模型仍可能凭对话里已有的信息作答。

事实成立时它直接放行、不问模型，所以认过人之后的每一句都不额外花钱。

### `no-leak` — 内部字段不外泄

```ts
{
  name: '内部字段不外泄',
  type: 'no-leak',
  tool: 'query_bill',
  field: '_internal_note',           // 产出里形如 `字段名=值`
  evals: { deny: [...], allow: [...], heldout: [...] },
}
```

抹掉之后模型也真的用不了这条信息，用户问到只能说查不到——这个代价要跟客户讲清楚。
不要改成「说话时检查有没有说出这个值」：实测模型复述工具产出时从不逐字，
按值匹配在泄得最彻底的那次完全失灵。

### `require-fallback` — 越界必须转出

```ts
{
  name: '越界兜底',
  type: 'require-fallback',
  outOfScope: '系统覆盖不了的事，如非运营学校、超出权限的问题',
  fallback: '说明超出范围或权限，并转相关部门',    // ← 只写「必须做什么」
  reply: '您这个问题超出了我的权限，我现在马上反馈相关部门。',
  provider: 'deepseek-official', model: 'deepseek-chat',
  evals: { deny: [...], allow: [...], heldout: [...] },
}
```

**`fallback` 里不要写「不得承诺」这类无条件禁止**，那半句拆成一条 `semantic-policy`。
拆出来的那条要写窄：写成「不得给出确定数字」会把「照实报账单金额」也拦掉；
写成「不得对**尚未发生**的结果、时间、金额做承诺；如实陈述已查到的事实不算」才两边都成立。

## 第 2 步：写验收用例（这一步只有人做得了）

每条声明三组，缺一组不算写完：

| 组 | 写什么 | 判什么 |
|---|---|---|
| `deny` | 必须被拦住的 | 这条规矩管不管用 |
| `allow` | 必须原样放行的 | **有没有过度拦截** |
| `heldout` | 语义同类、字面上跟 `deny` 不重叠 | **判别力全在这一组** |

**留出集怎么写**：想一个跟 `deny` 里那条**意思一样、但一个字都不重合**的说法。

```
deny    请登录 portal 查看
heldout 请登录后台管理系统查看      ← 同一件事，没有共同的词
```

**下面这些都不是留出用例**（机器会替你查出来，但先别写）：

```
✗ BOSS系统登录超时                      含着已声明的词，必中
✗ 这个不可能办到                        直接用了 policy 里举过的例词
✗ {before: [], call: 'query_network'}    免检工具，必不中，死用例
✗ {before: ['lookup_account'], say: …}   前置事实已成立，必不中，死用例
```

**`allow` 那一组不能省。** 过度拦截只有它抓得住——实测过一次：某条规矩写宽之后
必拦 3/3、留出 5/5，看着完美，把 `allow` 算进来才发现它把「照实报账单金额」也拦了。

*机器会替你查什么*：三组是否齐全、留出用例是不是伪装的（按类型各有检法）。
**语义上「是不是同一类」机器判不了，那一步只有你能做。**

## 第 3 步：登记表达不了的条款

```ts
export const BUNDLE: SpecBundle = {
  specs: [...],
  uncovered: [
    {
      clause: 'SOP 第 X 条：未认人不得回复账号相关内容',
      why: '内置类型只能按工具名判前置，判不了「这段话是不是在讲账号详情」。'
        + '声明只做到了取数据那一侧。',
    },
  ],
}
```

**空着几乎一定是漏了。** 一份真实 SOP 里总有几条落在内置类型之外——实测过一份，
六条声明之外还剩三条填不进去。

**这一栏是唯一一件用例兜不住的事。** 验收用例是检测器，检测不到没写进去的东西：
漏掉的条款不会有用例，报告因此全绿。上面那份 SOP 就是这样——「未认人不得回复账号
相关内容」表达不了、没写进声明，六条声明的报告一个红都没有，而那条规矩根本没上线。
拆条款和措辞的问题用例发现得了（数字会掉），只是怎么改要靠你；这一件用例连发现都
发现不了。

模型不会主动说「这条我表达不了」：给它一份 SOP 让它写声明，它会硬套一个够不着的类型，
换来稳定误拦。所以这一栏是给人留的。

*机器会替你查什么*：`uncovered` 空着会警告；条目缺 `clause` 或 `why` 直接拦住冻结。

---

## 第 4 步：跑两个命令

```
1. checkSpecHygiene(bundle)   机械体检，不花钱，不过就不该冻结
2. checkSpecEvals(ctx, specs) 验收用例，语义类要调模型
```

看第二步的报告：

- **必拦没满** → 这条规矩没管用，改声明
- **必放没满** → 过度拦截，把措辞写窄
- **留出没满** → 分两种：字面词表那一类是能力边界（该并挂语义判定）；
  语义类那一类是措辞不够，改 `policy` 再跑

**措辞是唯一没有机械检查的一环。** 同一条规矩、同一个模型、同一批用例，
声明里改半句话，判定结果就会变——实测过：`fallback` 里留不留半句无关的话，
必拦从 3/3 变成 6 轮漏 3 次。所以改完措辞一定要重跑，不能靠读。

---

## 交付前对一遍

- [ ] 每条 SOP 条款都有去向：填进某条声明，或登记进 `uncovered`
- [ ] 混写的条款拆开了（有条件的义务 / 无条件的禁止各一条）
- [ ] 每条声明三组用例齐全，留出集是自己想的、不是从 `deny` 改写的
- [ ] `checkSpecHygiene` 通过
- [ ] `checkSpecEvals` 的必拦、必放两组满分；留出集的数字记进交付记录
- [ ] 措辞改过之后重跑过
